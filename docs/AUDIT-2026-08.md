### 0.2 **확인하지 못한 것 (중요)**

**운영 DB와 운영 API에 접근할 수 없다.** 이 컨테이너의 egress 정책이 외부 호스트를 차단한다.

```
curl  https://addiction-society-api.onrender.com/api/sources/summary  → 연결 실패(000)
WebFetch 동일 URL → EGRESS_BLOCKED
```

따라서 이 보고서에서 **"운영 DB에 몇 건이 있다"고 단정한 문장은 하나도 없다.** 데이터 실태(2장)는
전부 "시드 정의 기준" 또는 "로컬 재현 기준"이며, 운영 실적재량은 **미확인**으로 표기하고
직접 돌릴 SQL을 함께 적었다. 이 구분을 지키는 것이 이 감사의 전제다.

표기 규칙:
- **[확인]** — 코드/로컬 실행으로 직접 검증함
- **[추정]** — 코드 근거는 있으나 운영 실물 미확인

**[확인]** 신규 DB에 마이그레이션 9종을 순서대로 적용해 대조했다. **9/9 전부 성공.**

### `documents`의 구조적 문제 [확인]

29건 중 **23건(79%)이 `sources` 레지스트리를 그대로 재투영한 것**이다.
`buildSourceCandidates()`가 소스 1건당 문서 1건을 자동 생성한다:

```
title       = source.titleKo        (동일)
sourceUrl   = source.url            (동일)
description = "{기관}({org}) 발간 · {종류} · 도메인 {domain}. 데이터 관측소 소스 레지스트리 대표 산출물."
year        = undefined             (전부 비어 있음)
```

즉 `/policy`는 `/sources`와 **같은 23건을 문장만 바꿔 다시 보여준다.** 블루프린트 제2장의
"질문이 겹치면 페이지가 겹친 것"에 정면으로 걸린다. 고유한 정책문서는 **법률 6건뿐이며,
그 6건도 `year`가 전부 null**이다.

### `indicators` 3건 — "지표"라 부를 수 있는가 [확인]

`kcgp-youth.data.json` 전문을 읽었다. 냉정한 평가는 **"아니다"**.

| 코드 | 값 | 기간 |
|---|---|---|
| `kcgp_youth_gambling_problem_rate` (위험군+문제군) | 4.8% | 2022 |
| `kcgp_youth_gambling_atrisk_rate` (위험군) | 3.9% | 2022 |
| `kcgp_youth_gambling_problem_group_rate` (문제군) | 0.9% | 2022 |

문제는 건수가 아니라 성격이다.

1. **3건은 독립 지표가 아니다.** `4.8 = 3.9 + 0.9`. 하나의 측정을 셋으로 쪼갠 것이다.
   실질 정보량은 **지표 1개**다.
2. **시계열이 없다.** 전부 2022년 단일 시점 → `/indicators/[code]`의 추이 차트는
   `hasTrend = totalSeries.length >= 2` 조건에 걸려 **세 페이지 모두 "추세 분석 준비 중"만 뜬다.**
3. **4년 묵었다.** 2026년 8월 기준 2022년 값이다. 2024년 회차가 이미 존재한다는 사실이
   데이터 파일 주석에 스스로 적혀 있다("2024 세부 비율... 후속").
4. **도메인이 하나다.** 전부 D1(도박). 알코올·마약·디지털 지표는 0건.
5. **딥링크가 값이 아니라 파일 목록 페이지를 가리킨다.** `source_url`이
   `data.go.kr/data/15142248/fileData.do` — 원칙3의 형식은 지켰지만 "클릭하면 그 숫자가 보인다"는
   취지는 못 지켰다.

정의(`definition_ko`)·방법주석(`method_note`)의 **서술 품질 자체는 높다.** 조사 승인번호까지 달려 있다.
문제는 그 훌륭한 그릇에 담긴 것이 4년 전 숫자 하나라는 점이다.

## #1 [치명] 익명 회원가입 → `admin` 권한 → 전체 쓰기 개방

**[확인 — 실제로 기동해 재현]**

```
POST /api/auth/register {"email":"attacker@example.com",...}  → 200, role= admin
POST /api/policy/documents  (그 토큰)                          → HTTP 201  ← 문서 생성됨
POST /api/indicators/observations/approve (그 토큰)            → HTTP 201  ← 검수 게이트 통과
POST /api/policy/documents  (토큰 없음)                        → HTTP 401
```

세 가지가 겹쳤다.

1. `POST /api/auth/register`에 **가드·초대코드·허용목록이 전혀 없다.**
2. `users.role`의 **DB 기본값이 `'admin'`**이다 (`@Column({ default: 'admin' })`).
3. **역할을 검사하는 코드가 레포 전체에 없다.** `JwtAuthGuard`는 토큰 유효성만 본다.

결과: 누구든 회원가입 한 번으로 policy/research/recovery/tags 전체 생성·수정·삭제,
**관측치 승인(원칙8 검수 게이트)**, PDF 추출 트리거, 파일 업로드 권한을 얻는다.
감사 중 만든 계정으로 실제로 `AUDIT TEST` 문서가 로컬 DB에 들어갔다.

가중 요인: `main.ts`가 `origin: '*'`로 CORS 전면 허용, rate limit·helmet 없음(의존성에 `throttler`·`helmet` 부재).

> **[미확인]** 운영 배포본에 이 코드가 그대로 올라가 있는지는 egress 차단으로 확인 못 했다.
> 배포된 것이 `main`이라면 그대로 성립한다. **가장 먼저 직접 확인할 것:**
> ```
> curl -s -X POST https://addiction-society-api.onrender.com/api/auth/register \
>   -H 'Content-Type: application/json' \
>   -d '{"email":"probe@example.com","password":"probe1234","name":"probe"}'
> ```
> 토큰이 돌아오면 즉시 조치 대상. (확인 후 그 계정은 지울 것)

## #8 [중간] `/timeline`은 정상 운영 중에도 빈 페이지다

**[확인]** `SIGNIFICANT = [published, changed, stale, failed, manual, rescheduled]`.

  보여주는 정보가 화면에서 가려진다.**

"연대기"라는 이름의 페이지가 영구히 비어 있으면 원칙1("없으면 수집 중")은 지켰어도
페이지 존재 이유가 사라진다.

> **[미확인]** 운영에서 `source_events`가 실제로 쌓이고 있는지 확인 불가.
> ```sql
> SELECT event_type, count(*), max(detected_at) FROM source_events GROUP BY 1 ORDER BY 2 DESC;
> ```
> 이 결과가 비어 있으면 **크론이 한 번도 안 돌았다는 뜻**이므로 최우선 조사 대상이다.

## #9 [중간] 알림 오탐 위험이 구조적으로 남아 있다

| board-latest (목록 첫 행 제목+날짜) | 2 | **강함** |

> **[미확인]** 재발 여부는 `source_events`의 `changed` 이벤트 빈도로 판정 가능하다.
> ```sql
> SELECT source_id, count(*) FROM source_events
> WHERE event_type='changed' AND detected_at > now() - interval '30 days'
> GROUP BY 1 HAVING count(*) > 2 ORDER BY 2 DESC;
> ```
> 같은 소스가 월 3회 이상 `changed`면 오탐으로 봐야 한다(연간 발간물이 월 3회 바뀔 리 없다).

| 8 | 검수 없는 자동 게시 금지 | ❌ **위반** | `?status=all` 공개 우회(#6) + 누구나 승인 API 호출 가능(#1) |
| 9 | 콘텐츠 복제 축적 금지 | 🔸 | Statory는 순수 프록시로 준수. 단 **내부에서** documents가 sources를 복제(#2.2) |
| 10 | 비밀값 노출 금지 | ✅ 준수 | 전 히스토리 스캔 결과 웹훅·키·DSN **0건**. `.gitignore` 적절, `.env.example`은 값 없음 |
| 11 | 감지·감시 이력 보존 | 🔸 | 구조는 있으나 정본 문서에 미기재(#15), 실제 적재 [미확인](#8) |

# 제4부. 제안

## 4.1 지금 가장 시급한 3가지

### 1순위 — 인증 잠그기 (문제 #1)

**근거**: 유일한 "지금 당장 피해가 발생 중일 수 있는" 항목이다. 나머지는 전부
"기능이 부족하다"인데 이것만은 "제3자가 데이터를 조작할 수 있다"이다.
관측소는 신뢰가 제품인데, 외부인이 승인 API를 눌러 미검수 값을 게시할 수 있다는 사실
하나로 원칙8이 무의미해진다.

최소 조치(작은 순서):
1. `POST /api/auth/register`를 막는다 — 환경변수 초대코드 또는 아예 비활성화 후 계정은 시드로 생성.
2. `users.role` 기본값을 `'viewer'`로 바꾸고, 쓰기 엔드포인트에 `RolesGuard('admin')`를 건다.
3. CORS `origin`을 사이트 도메인으로 좁힌다.
4. 운영 DB의 `users`를 조회해 모르는 계정이 있는지 확인하고, 있으면 그 계정이 만든 행을 감사한다.

### 2순위 — 데이터 재현성 확보 (문제 #5)

**근거**: 이 프로젝트가 스스로 지목한 사망 원인이 "갱신 중단"이다. 현재 운영 데이터의
대부분은 **사람이 언젠가 손으로 돌린 스크립트의 산물**이라 DB를 잃으면 복구 절차가
누구의 기억에도 온전히 남아 있지 않다. 기능을 더 만들기 전에 지금 있는 것부터
재현 가능하게 만들어야 한다.

- `seed:recovery`·`seed:documents`·`collect:research`·`collect:indicators`를
  `deploy-init`에 편입하거나(전부 멱등이므로 기술적으로 가능),
  최소한 **"DB를 처음부터 세우는 명령 순서"를 `DEPLOY-RUNBOOK.md`에 한 블록으로** 적는다.
- 먼저 운영 DB에서 2.2의 각 테이블 건수를 실제로 조회해 **무엇이 이미 들어 있는지부터 확정**한다.

### 3순위 — 지표 1개를 제대로 완성 (문제 #4)

**근거**: `/indicators`는 관측소의 간판인데 세 페이지 모두 "추세 분석 준비 중"이다.
새 도메인을 넓히는 것보다 **하나를 시계열로 완성해 "이 사이트에 오면 다른 데 없는 걸 볼 수 있다"는
증거를 하나 만드는 것**이 우선이다. 지표 30개가 각각 1점이면 여전히 아무것도 아니지만,
지표 1개가 2018~2024 6점이면 그건 인용 가능한 자산이다.

구체적으로: `kcgp_youth`의 2024 회차부터 채우고, 과거 회차를 역순으로 확보한다.
이것이 곧 PDF 파이프의 첫 완주(#10)이기도 하다.

## 4.2 관측소(데이터 깊이) vs 중독사회(해석·목소리)

**판단: 앞으로 3~6개월은 관측소에 무게를 둔다. 단 "넓이"가 아니라 "깊이"로.**

코드·데이터가 말해주는 근거:

1. **해석 쪽은 인프라가 0이다.** 글을 쓰고 발행할 수단이 레포에 없다 — CMS도, 에디터도,
   `posts` 테이블도 없다. `/about`은 빈 자리표시자다. `/lab`은 남의 보고서 프록시다.
   지금 "목소리"로 방향을 틀면 **처음부터 새로 만들어야 한다.**
2. **관측소 쪽은 골격이 90% 완성이고 내용물이 10%다.** 스키마·크론·원장·검수 게이트·
   PDF 엔진·UI가 전부 있는데 지표가 3건(실질 1건)이다. **이미 지은 집에 아직 아무것도
   안 들여놓은 상태**라 한계효용이 압도적으로 높다.
3. **해석은 데이터가 있어야 설득력이 생긴다.** "청소년 도박이 문제다"는 누구나 쓴다.
   "2018년 X%에서 2024년 Y%로, 같은 기간 예산은 Z% 줄었다"는 이 사이트만 쓸 수 있다.
   그 문장을 쓰려면 시계열이 먼저다.

다만 **깊이가 아니라 넓이로 가는 것은 반대한다.** 소스를 23 → 40으로 늘리는 것은
감시 사각지대(#3)와 오탐(#9)만 비례해서 키운다. 지금 필요한 건 소스 추가가 아니라
**등록된 23건에서 실제로 값을 뽑아내는 일**이다.

## 4.3 M4(대검 월간동향) 착수 준비도

**평가: 인프라는 형태상 준비됐으나 실증이 0이라 "아직 아니다".**

| 항목 | 상태 |

**권고 순서**: M4를 바로 시작하지 말고 **`kcgp_youth`로 PDF 파이프를 한 번 끝까지
완주(추출 → pending 적재 → 검수 → 게시)한 뒤** 그 경험으로 대검 어댑터를 쓴다.
검증 안 된 파이프에 두 번째 소스를 얹으면 실패 원인이 소스 문제인지 파이프 문제인지
구분할 수 없다. 완주 1회 후에는 어댑터 추가만 하면 되므로 **M4 자체는 가벼운 작업**이 된다.

전제 조건 하나: **검수 UI(#7)가 없으면 M4는 지속 불가능하다.** 월간 소스는 매달 pending이
쌓이는데 승인 수단이 curl뿐이면 두세 달 안에 적체된다.

## 4.4 6개월 뒤 실패한다면, 가장 유력한 원인

**"데이터가 안 쌓여서, 다시 올 이유가 없는 사이트가 된다."**

이것이 가장 유력하다고 보는 이유는 심증이 아니라 코드에 남은 구조 때문이다.

1. **모든 적재 경로가 사람의 수동 실행에 의존한다.** `deploy-init`이 자동 보장하는 것은
   소스 레지스트리뿐이다. 지표·연구·회복자원·정책문서는 전부 "누가 스크립트를 돌려야"
   들어온다. 자동으로 도는 크론 2개는 **감시만 하고 값을 수집하지 않는다.**
   즉 **아무도 아무것도 안 해도 데이터가 늘어나는 경로가 현재 0개다.**
2. **유일하게 자동 수집이 될 수 있었던 PDF 크론은 기본 off이고, env 선언조차 없다.**
3. **검수 UI가 없어서 자동 수집을 켜도 pending이 적체된다.** 파이프를 켜는 순간
   병목이 사람에게 넘어오는데 그 사람에게 도구가 없다.
4. 블루프린트가 이미 같은 진단을 내려놨다 — *"사망 원인 1위는 트래픽 부족이 아니라 갱신 중단
   (GDPI 2021, ATLAS-SU 2014의 전철)."* 지금 구조는 그 전철을 밟도록 되어 있다.

증상은 이렇게 나타날 것이다: 6개월 뒤에도 지표는 3건이고, `/timeline`은 여전히 비어 있고,
`/indicators`는 여전히 "추세 분석 준비 중"이며, 사이트는 잘 만들어졌지만 볼 것이 없다.
UI를 네 번 다듬는 동안(UI-1~4) 지표가 3건에서 3건이었다는 사실이 이미 그 방향을 가리킨다.

**차순위 실패 원인**: 보안 사고로 인한 데이터 오염(#1). 확률은 낮지만 발생하면
"관측소가 조작됐다"는 사실 자체가 신뢰를 회복 불가능하게 만든다. 발생 확률 × 회복 불가능성으로는
1순위 조치 대상이다.

## 부록. 운영 DB에서 직접 확인해야 할 것들

이 감사가 접근하지 못한 부분이다. 순서대로 돌리면 **[미확인]** 항목이 전부 채워진다.

```sql
-- 1) 테이블별 실적재량 (2장 확정)
SELECT 'sources' t, count(*) FROM sources UNION ALL
SELECT 'documents', count(*) FROM documents UNION ALL
SELECT 'research', count(*) FROM research UNION ALL
SELECT 'recovery_resources', count(*) FROM recovery_resources UNION ALL
SELECT 'indicators', count(*) FROM indicators UNION ALL
SELECT 'observations', count(*) FROM observations UNION ALL
SELECT 'source_events', count(*) FROM source_events UNION ALL
SELECT 'users', count(*) FROM users ORDER BY 1;

-- 2) 크론이 실제로 도는가 (문제 #8)
SELECT event_type, count(*), max(detected_at) FROM source_events GROUP BY 1 ORDER BY 2 DESC;

-- 3) 알림 오탐 재발 (문제 #9) — 연간 발간물이 월 3회 바뀌면 오탐
SELECT source_id, count(*) FROM source_events
WHERE event_type='changed' AND detected_at > now() - interval '30 days'
GROUP BY 1 HAVING count(*) > 2 ORDER BY 2 DESC;

-- 4) 검수 적체 (문제 #6·#7)
SELECT status, count(*) FROM observations GROUP BY 1;
SELECT status, count(*) FROM research GROUP BY 1;

-- 5) 예정일 교정 반영 (AS-M3-FIX-DATE)
SELECT count(*) FROM sources WHERE next_expected_at < date_trunc('month', CURRENT_DATE);

-- 6) 침입 흔적 (문제 #1) — 모르는 계정이 있는가
SELECT id, email, name, role, created_at FROM users ORDER BY created_at;
```
